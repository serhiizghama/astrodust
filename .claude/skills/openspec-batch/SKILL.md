---
name: openspec-batch
description: Прогоняет список OpenSpec-изменений по полному циклу без участия человека - apply, проверки, ревью, sync, archive - по одному изменению за раз, в заданном порядке. Использовать, когда просят "выполни эти изменения подряд", "прогони change'и до архива", "сделай всё сам по списку".
allowed-tools: Bash, Read, Edit, Write, Glob, Grep, Skill, TodoWrite
---

Автономный конвейер по списку изменений: одно изменение проходит весь путь до архива,
только потом начинается следующее. Человек не подтверждает ничего по ходу —
вмешательство нужно лишь при жёсткой остановке (список ниже).

**Вход:** имена изменений через пробел или запятую, в том порядке, в котором их выполнять.
`/openspec-batch add-inventory-and-credits add-separator-building`

**Флаги:**
- `--dry-run` — только префлайт и план, ни одной правки кода.
- `--commit` — коммитить каждое изменение отдельным коммитом после успешного архива.
  По умолчанию ВЫКЛЮЧЕН. Включается только если пользователь сам написал флаг в этом вызове.
  Автор — пользователь, без AI-атрибуции, без `Co-Authored-By`, без push.

## Инварианты на весь прогон

- Порядок задан пользователем. Не переставлять его молча.
- Изменения не смешиваются: следующее не начинается, пока предыдущее не заархивировано
  или прогон не остановлен.
- Никогда: `git push`, `git commit --amend`, `rebase`, `reset --hard`, удаление веток,
  правки в БД, любые записи в ClickUp.
- `git commit` — только при явном `--commit` в этом вызове.
- Не откатывать чужие изменения в рабочем дереве. Файлы, не относящиеся к текущему change,
  не трогать.
- Ничего не считать сделанным без запуска проверок. Если проверку не удалось выполнить —
  сказать об этом прямо, а не «должно работать».

## Фаза 0. Префлайт (один раз, до любых правок)

1. `openspec list --json` — убедиться, что каждое имя из списка существует и активно
   (не в архиве). Неизвестное имя → жёсткая остановка, ничего не начинать.
2. `git status --short` — зафиксировать исходное состояние дерева. Если дерево грязное,
   перечислить файлы и продолжать: они станут фоном, который нельзя приписывать change'ам.
3. **Проверка зависимостей.** Прочитать `tasks.md` и `proposal.md` каждого изменения из списка
   и найти явные требования порядка (в этом проекте такие пункты формулируются словами
   «убедиться, что `<change>` реализован и заархивирован раньше»). Для каждого названного
   предшественника: если он всё ещё активен в `openspec list --json` и его нет в
   `openspec/changes/archive/` — жёсткая остановка с объяснением, ДО начала работы.
   Также проверить порядок внутри самого списка: если B зависит от A, а A идёт позже — остановка.
4. **Базовая линия.** `npm run typecheck` и `npm test`. Если красно уже сейчас — остановка:
   иначе чужую поломку припишем первому же change'у.
5. Показать план: список изменений, число задач в каждом, порядок, что проверяется.
   При `--dry-run` — закончить здесь.

## Фазы 1–6 (для каждого изменения по очереди)

### 1. Apply

Выполнить рабочий процесс скилла `openspec-apply-change` для этого имени, целиком, до
последней задачи. Ключевое отличие от одиночного запуска: **пользователь заранее одобрил
весь цикл**, поэтому «пауза и вопрос» заменяется на решение по правилам ниже. Отмечать
`- [ ]` → `- [x]` сразу после каждой задачи — это единственный носитель прогресса, если
сессия прервётся.

Задачи-«убедиться, что …» и задачи-замеры — это работа, а не формальность: под них пишется
проверка в `tests/` или запускается `npm run bench` / `npm run shot`, а результат называется
числом. Отметить такую задачу без запуска — соврать о готовности.

### 2. Проверки

По порядку, после последней задачи change'а:

1. `npx prettier --write` по файлам, которых коснулся этот change (не по всему проекту).
2. `npm run typecheck`
3. `npm test`
4. `npm run build`
5. Если затронут рендер — `npm run shot <change-suffix>` и сравнить с `shots/` глазами.
   Если затронут звук — `npm run verify:audio`.

Красный результат чинится здесь же: до 3 попыток на одну падающую проверку. Чинить причину,
а не тест. Если после 3 попыток красно — жёсткая остановка, архив не делать.

### 3. Ревью

1. `openspec validate --change "<name>"`.
2. Пройти по дельта-спекам change'а (`artifactPaths.specs.existingOutputPaths` из
   `openspec status --change "<name>" --json`) и для каждого требования и сценария назвать
   конкретное подтверждение: файл со строкой или имя проверки. Сценарий без подтверждения —
   недоделанная задача: вернуться к фазе 1 для неё (один такой круг, дальше — остановка).
3. `git diff --stat` — убедиться, что диффом задет только объём этого change'а.
4. Перечитать свой дифф на предмет мусора: отладочные логи, закомментированный код,
   заглушки «TODO позже», случайно переформатированные чужие файлы.

### 4. Sync

Выполнить рабочий процесс скилла `openspec-sync-specs` для этого change'а: осмысленно влить
дельты в `openspec/specs/<capability>/spec.md`. Именно до архива — архив переносит папку
change'а, и после переноса синхронизировать будет уже нечего.

Затем перепроверить каждую затронутую capability: ADDED на месте, MODIFIED применены с
сохранением несмежных сценариев, REMOVED убраны, RENAMED переименованы. Несовпадение —
жёсткая остановка, архив не делать.

### 5. Archive

Выполнить рабочий процесс скилла `openspec-archive-change`. Его встроенные вопросы уже
отвечены этим прогоном:

| Вопрос скилла архива | Ответ этого прогона |
|---|---|
| Незавершённые артефакты — продолжать? | Да, если статус `done`/`skipped`; иначе остановка |
| Незавершённые задачи — продолжать? | Нет. Незакрытая задача = остановка, а не архив с оговоркой |
| Дельты не синхронизированы | Остановка: фаза 4 обязана была это сделать |
| Дельты синхронизированы — архивировать? | «Archive now» |
| Целевая папка архива уже существует | Остановка, не перезаписывать |

### 6. Итог по изменению

Короткая сводка: сколько задач, что показали проверки (числом, не «ок»), какие capability
обновлены, куда переехал change. При `--commit` — здесь коммит от имени пользователя, без
AI-атрибуции и без push. Затем сразу начать следующее изменение из списка, без вопросов.

## Что считать жёсткой остановкой

Останавливать весь прогон, сообщать состояние и ждать человека:

- Неизвестное имя change'а или нарушенная зависимость между change'ами (фаза 0).
- Красная базовая линия до начала работы.
- Проверка остаётся красной после 3 попыток починки.
- Задача допускает два прочтения, дающие разное наблюдаемое поведение, и дельта-спека
  не разрешает выбор. Угадывать нельзя.
- Реализация вскрыла противоречие в proposal/design/specs — нужно править план, а не код.
- Конфликт дельта-спеки с основной спекой при sync.
- Требуется что-то необратимое или выходящее за объём change'а.

При остановке: что сделано, где именно встали, что уже заархивировано, что остаётся в
рабочем дереве, какие изменения из списка ещё не начаты. Незавершённое НЕ архивировать
и НЕ откатывать — работа остаётся в дереве, решение за пользователем.

## Формат хода

Держать TodoWrite-список из фаз текущего change'а и после каждой фазы печатать одну строку
журнала, чтобы прогресс читался при прокрутке:

```
[1/2] add-inventory-and-credits · apply     58/58 задач
[1/2] add-inventory-and-credits · проверки  typecheck ok · test ok · build ok
[1/2] add-inventory-and-credits · ревью     6 capability, 41 сценарий подтверждён
[1/2] add-inventory-and-credits · sync      pixel-world, terrain-digging, player-inventory
[1/2] add-inventory-and-credits · archive   → archive/2026-08-08-add-inventory-and-credits
[2/2] add-separator-building    · apply     …
```

Финальная сводка в конце всего прогона: по каждому изменению — заархивировано / остановлено
на фазе N, и одна строка про состояние рабочего дерева.

## Возобновление

Прогон восстанавливается по состоянию на диске, отдельного файла состояния нет.
`openspec list --json` показывает, что уже уехало в архив, галочки в `tasks.md` — где
остановился apply. Повторный вызов с тем же списком продолжает с первого незаархивированного
изменения, пропуская выполненные задачи.
